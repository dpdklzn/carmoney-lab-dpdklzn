# Проверка скилла requirements (2.2.2)

## Условия

Трек: аналитик. Две новые сессии Kilo code / MiniMax M3, одна и та же просьба без слова «скилл»:

```text
Подготовь требования к задаче LOAN-12 по материалам docs/sources/LOAN-12.md.
```

В первом запуске папка requirements была доступна и Kilo ранее показывал её в Discovered Skills. Для второго запуска папка временно вынесена из .kilo/skills/, первый файл результата также вынесен из репозитория, чтобы не подсказывать формат. После второго запуска папка скилла возвращена. Отдельный блок вызова skill → requirements первого запуска пока не предоставлен: совпадение формата не доказывает автоматическую загрузку.

## Сравнение

| Признак | С папкой requirements | Без папки requirements |
|---|---|---|
| Разделы | Требования / Границы / Не-цели / Открытые вопросы | Замысел / Зачем / Constraints / Open questions / Не входит |
| Файл результата | docs/spec/spec_LOAN-12.md | docs/intent/intent_LOAN-12.md |
| Ответ в чате | Пользователь предоставил требования в выбранном формате | Пользователь предоставил сводку создания intent |
| Ориентир | Формат пользовательской рутины | Существующий intent_MILEAGE.md и процесс репозитория |
| REQ/AC и план реализации | Не добавлены | Не добавлены, но выбран другой тип документа |

Вывод в одну строку: с доступным requirements агент использовал мои четыре раздела и путь docs/spec/spec_<ID>.md; без него выбрал пятираздельный intent и путь docs/intent/intent_LOAN-12.md.

## Качество и ограничения

Оба результата содержат ложное противоречие для возраста ровно 7 лет: «старше 7» и «свыше 7 до 12 включительно» оба исключают ровно 7 лет, сами по себе они не дают разные пределы для этого возраста. Формат со скиллом не гарантирует правильного анализа источников. Первый результат также содержит детали тестирования, хотя скилл должен только переформулировать требования; текст «год в будущем ... проходит существующую валидацию» двусмысленен и не фиксирует явно отказ. Ответы ниже сохранены без исправления, чтобы сравнение отражало фактическую работу агента, а не редактуру помощника.

Description скилла в этом эксперименте не менялось. Подтверждение автоматического вызова skill в первой сессии остаётся необходимым для полной проверки условия задания.

## Ответ с доступным скиллом

Текст сохранённого файла первого запуска:

```markdown
# Требования LOAN-12

## Требования

- При принятии решения по заявке учитывать возраст предмета залога, чтобы старый автомобиль нельзя было заложить под тот же процент от стоимости, что и новый.
- Возраст автомобиля считать в полных годах как `год текущий − год выпуска` (П-1).
- Предельный LTV по возрасту (П-2):
  - до 3 лет — 70 %;
  - до 7 лет — 60 %;
  - до 12 лет — 50 %;
  - до 20 лет — 40 %.
- Автомобиль старше 20 лет в залог не принимается — решение `reject` независимо от LTV (П-3).
- Если рассчитанный LTV превышает предельный для возраста — заявка не отклоняется автоматически, а уходит в `review` (П-4).
- Общие пороги решения по LTV сохраняются: ≤ 60 % — `approve`, 60–85 % — `review`, > 85 % — `reject`. Возрастной лимит применяется **после** них и может только ужесточить решение, но не смягчить (П-5).

## Границы

- Применяется к процессу предварительной оценки заявки на заём под ПТС: на входе VIN, год выпуска, пробег, оценочная стоимость, запрошенная сумма, срок; на выходе — решение `approve`/`review`/`reject`.
- LTV считается как отношение запрошенной суммы к оценочной стоимости в процентах.
- Возраст ТС рассчитывается на текущий календарный год (в примерах источника — 2026).
- Учитываются пограничные случаи, перечисленные в источнике:
  - LTV ровно 60,0 % при возрасте ровно 3 года (проверяется двумя тестами);
  - год выпуска в будущем — опечатки вида 2062 вместо 2026, проходит существующую валидацию;
  - оценочная стоимость 0 или пустая — деление на ноль при расчёте LTV;
  - граница диапазона возраста (например, автомобиль 2019 года в 2026-м — 7 лет);
  - возраст ровно 20 лет.
- В источнике уже есть справочник предельных LTV по возрасту в `backend/config/rules.php` (ключ `ltv_by_age`), который сейчас не используется и должен быть задействован.

## Не-цели

- Не менять общие пороги решения по LTV (60 % и 85 % из П-5).
- Не менять способ расчёта LTV как отношение запрошенной суммы к оценочной стоимости.
- Не вмешиваться в валидацию VIN — это зона LOAN-09 (закрыт).
- Не реализовывать журнал решений и ручное рассмотрение андеррайтером — это зона LOAN-15 (в работе, связанный тикет).
- Не менять политику работы с очередью андеррайтера и порог её перегрузки.
- Не определять источник «текущего года» сверх того, что он уже используется в системе.

## Открытые вопросы

1. **Действие при превышении предельного LTV по возрасту.**
   Источники расходятся:
   - `[TICKET-LOAN-12]` (18.09.2026, риск): при превышении — **отказывать**, «на андеррайтера такие заявки не гнать, у них и так очередь».
   - `[REG-LTV-07]` п. 3.4 (ред. 04.2026): превышение предельного значения не является основанием для автоматического отказа, заявка передаётся на **ручное рассмотрение** андеррайтеру с указанием величины превышения.
   - П-4 раздела 2 следует регламенту и противоречит тикету.
   Контекст `[CONF-underwriting-queue]` (11.09.2026): средняя очередь андеррайтера — 40 заявок, порог перегрузки — 60.
   Владелец вопроса — риск-менеджер.

2. **Граница диапазона «7 лет».**
   - П-2: «до 7 лет — 60 %» — без явного указания включительно/исключительно.
   - `[TICKET-LOAN-12]`: «старше 7 лет — 50 %».
   - `[REG-LTV-07]` п. 3.2: «до 3 включительно — 70 %», «свыше 3 до 7 включительно — 60 %», «свыше 7 до 12 включительно — 50 %».
   Для автомобиля ровно 7 лет предел разный (60 % vs 50 %); в источнике ответа нет.

3. **Граница возраста 20 лет.**
   - П-3: «старше 20 лет» — формулировка строго больше.
   - Справочник в коде упоминается как `max_age: 20` (подсказка ведущему).
   - `[REG-LTV-07]` п. 3.2: «свыше 20 — не принимается» — тоже строго больше.
   Для автомобиля ровно 20 лет итоговое поведение по справочнику в коде требует сверки.

4. **Содержимое `ltv_by_age` в `backend/config/rules.php`.**
   В источнике указано, что справочник уже лежит в конфиге и никем не используется, но его текущее содержимое не приведено. Требуется сверить с таблицей из `[REG-LTV-07]` п. 3.2 до начала реализации.

5. **Допустимость единого автотеста на двух границах.**
   Источник отдельно отмечает, что LTV 60,0 % и возраст 3 года одним тестом не проверяются — нужно два. Это влияет на объём тестового покрытия, но не на формулировку требований; зафиксировано здесь для прозрачности.
```

## Ответ без скилла

Текст сохранённого файла второго запуска:

```markdown
# Intent: учёт возраста автомобиля при расчёте решения по заявке

ID задачи: `LOAN-12`. Источник: `docs/sources/LOAN-12.md`, разделы 1–5.
Конфликты между фрагментами зафиксированы как Open questions, не «починены».

## Замысел

Принять возраст автомобиля как фактор решения по заявке (`approve` / `review` /
`reject`): рассчитать полный возраст как `текущий_год − год_выпуска`, определить
предельный LTV по диапазону возраста из регламента, поверх общего LTV-порога
применить возрастной лимит, который может только ужесточить итог. Авто старше
максимального возраста — `reject` независимо от LTV. — источник: раздел 1;
раздел 2, П-1 … П-5.

## Зачем

Сегодня возраст не участвует в расчёте: справочник `ltv_by_age` лежит в
`backend/config/rules.php` и не используется (раздел 1). По выгрузке II кв. 2026
предел 50 % для группы 8–12 лет фактически не соблюдается — средний LTV 63 %;
доля просрочки 30+ для группы 13–20 лет — 9,4 %, для 21+ — 21,7 %. Цель —
выровнять риск по старым залогам. — источник: [DATA-ltv-age-2026Q2] и комментарий
к выгрузке.

## Constraints

- Возраст — полных лет, `текущий_год − год_выпуска`. — раздел 2 П-1;
  [REG-LTV-07] п.3.5.
- Справочник предельных LTV по возрасту уже есть в конфиге и не меняется
  по составу диапазонов в этой задаче: до 3 — 70 %, до 7 — 60 %, до 12 — 50 %,
  до 20 — 40 %; свыше 20 — не принимается. — раздел 2 П-2, П-3;
  [REG-LTV-07] п.3.2; код: `backend/config/rules.php`, ключ `ltv_by_age`.
- Превышение предельного LTV для возраста → заявка передаётся в `review`,
  а не отклоняется автоматически. — раздел 2 П-4; [REG-LTV-07] п.3.4.
  Конфликт с [TICKET-LOAN-12] — см. Open questions.
- Общие пороги по LTV сохраняются и применяются первыми: ≤ 60 % — `approve`,
  60–85 % — `review`, > 85 % — `reject`; возрастной лимит может только
  ужесточить итог. — раздел 2 П-5; код: `backend/config/rules.php` (`ltv`).
- Расчёт возраста ведётся на 2026 год в материалах; в коде — на текущий
  календарный год. — раздел 3; производное из П-1.
- В журнал решений (задача LOAN-15) добавляются LTV, применённый предел по
  возрасту, итоговое решение и сработавшее правило; ПДн заявителя не пишем.
  Формат и тесты журнала — в LOAN-15, не здесь. — [TICKET-LOAN-15].
- Существующая валидация года выпуска и стоимости остаётся как есть
  (год в будущем, опечатка 2062 → 2026, и т. п. — ошибка валидации, до
  расчёта решения не доходит). — раздел 4.
- Решение остаётся одним из `approve` / `review` / `reject`; новых полей и
  кодов в ответе API не добавляем в рамках LOAN-12 (LOAN-15 — отдельно).
  — производное из раздела 1 и состава участников.

## Open questions

- **Действие при превышении предела по возрасту.** [REG-LTV-07] п.3.4 требует
  передавать в `review` (ручное рассмотрение), [TICKET-LOAN-12] — отказывать
  сразу (мотив — перегрузка очереди андеррайтинга: средняя очередь 40, порог
  перегрузки 60, [CONF-underwriting-queue]). Статус: **открыт**, владелец —
  риск-менеджер (Никитина О., автор [TICKET-LOAN-12]).
- **Границы диапазонов возраста.** [REG-LTV-07] п.3.2 — «до 3 включительно»,
  «свыше 3 до 7 включительно», «свыше 7 до 12 включительно», «свыше 12 до 20
  включительно»; [TICKET-LOAN-12] — «старше 7 лет — 50 %», «старше 12 лет —
  40 %». Для авто ровно 7 лет это разные пределы (60 % против 50 %).
  Статус: **открыт**, владелец — риск-менеджер.
- **Возраст ровно 20 лет.** Раздел 2 П-3 — «старше 20 лет»; код
  (`max_age: 20`) и [REG-LTV-07] п.3.2 — «свыше 20». Граница ровно 20 —
  принимается или нет. Статус: **открыт**, владелец — риск-менеджер.
- **Оценочная стоимость 0 или пустая.** Деление на ноль при расчёте LTV.
  Поведение сейчас — в scope LOAN-12 или вне её. Статус: **открыт**,
  владелец — разработчик.
- **Где фиксируются поля журнала (LOAN-15).** Состав полей задан в
  [TICKET-LOAN-15] (id, LTV, предел по возрасту, решение, правило); формат
  хранения и тесты — отдельно. Статус: **открыт** как граница scope,
  владелец — риск-менеджер / разработчик.
```
