# Команда requirements (2.4.1)

Файл команды: `.kilo/commands/requirements.md`. Она явно запускает рутину из `.kilo/skills/requirements/SKILL.md`, а не полагается на автоматический выбор скилла. Формат скилла не скопирован в команду: указан раздел «Формат результата» исходной инструкции.

## Пример вызова

После Reload Window в новой сессии Kilo code / MiniMax M3:

```text
/requirements LOAN-12 docs/sources/LOAN-12.md
```

Ожидается вывод в чат и `docs/spec/spec_LOAN-12.md` с четырьмя разделами пользовательской рутины. Неподтверждённые числа не придумываются, разногласия остаются вопросами, код и тесты не меняются. При отсутствии ID или материала команда запрашивает уточнение.

## Проверка вызова

После инструкции вызвать команду пользователь предоставил ответ и сообщил об изменённом файле `docs/spec/spec_LOAN-12.md`. Сохранённый файл проверен: есть разделы «Требования», «Границы», «Не-цели», «Открытые вопросы». Вопросы содержат владельцев и ссылки на фрагменты исходных материалов. Нумерации REQ/AC и реализации кода нет. Исходный результат не отредактирован помощником.

На вопрос о прошлых действиях без нового исполнения агент подтвердил фактический вызов инструмента `skill` с параметром `name: "requirements"`: результат вернул SKILL.md внутри `<skill_content>`, отдельного Read SKILL.md не было. Исходную строку slash-команды агент со своей стороны не видит: он получил развёрнутую пользовательскую инструкцию. Это не является отказом загрузки скилла; вызов skill подтверждён сообщением агента, а строка `/requirements LOAN-12 docs/sources/LOAN-12.md` выше — инструкция запуска в интерфейсе Kilo. Отдельный скриншот исходного slash-ввода не предоставлен.

Для сравнения: ручной запуск с доступным requirements использовал разделы «Требования / Границы / Не-цели / Открытые вопросы» и путь `docs/spec/`; без скилла агент выбрал пятираздельный intent и `docs/intent/`. Качество фактических требований проверяется отдельно от совпадения формата.

## Сравнение результата с ручным прогоном

| Признак | Ручной запрос со скиллом (2.2.2) | Результат после команды |
|---|---|---|
| Формат и путь | Четыре пользовательских раздела, docs/spec/spec_LOAN-12.md | Сохранены те же разделы и путь |
| План реализации и REQ/AC | Не добавлены | Не добавлены |
| Источники | Ссылки на П-1…П-5 и фрагменты материалов | Ссылки на П-1…П-5, разделы и фрагменты материалов |
| Граница 7 лет | Ложное противоречие между «старше 7» и «до 7 включительно» | Ошибка повторилась: «старше 7» неверно включает ровно 7 лет |
| Граница 20 лет | Непроверенное сомнение об off-by-one | Недоказанное противоречие повторилось: max_age: 20 само по себе не противоречит «старше 20» |

Команда воспроизводит пользовательский формат ручного прогона, но не обеспечивает корректность анализа источников. В результате также есть утверждение, что будущий год проходит текущую валидацию, без подтверждённого чтения кода; это нельзя считать проверенным поведением сервиса. Упоминания двух отдельных тестов в разделе границ выходят за чистую переформулировку требований, хотя новой тестовой реализации не создано.

Итог: получены результат после инструкции запуска команды, четыре нужных раздела и подтверждение вызова skill requirements. Замечания к качеству сохранены для следующих проверок; ответ не принимается как согласованная новая бизнес-спецификация LOAN-12.

## Параметр пути (2.4.2)

В команду передаётся путь через `$ARGUMENTS`. ID берётся из отдельного аргумента или явного идентификатора в заголовке материала; при неоднозначности запрашивается. Пустой параметр не заменяется последней задачей или текущим открытым файлом: команда должна попросить путь и остановиться до ответа.

Два контрольных вызова, каждый в новой сессии code / MiniMax M3 после Reload Window:

| Вызов | Ожидаемая зависимость результата от параметра | Фактический результат |
|---|---|---|
| `/requirements docs/sources/LOAN-12.md` | Требования по возрастным лимитам, ID LOAN-12, файл docs/spec/spec_LOAN-12.md | Пользователь предоставил результат: четыре раздела, возрастные пределы 70/60/50/40%, общие пороги LTV, вопросы по источникам; назван файл docs/spec/spec_LOAN-12.md. |
| `/requirements docs/sources/CASE-01.md` | Требования по риск-проверкам заявки, ID CASE-01, файл docs/spec/spec_CASE-01.md | Получен ответ по лимитам сумм по типу ТС, числу активных займов, отказам и эскалации; назван файл docs/spec/spec_CASE-01.md. При последующей обработке ID взят из заголовка, существующий файл перезаписан результатом CASE-01. |

Дополнительная проверка в третьей новой сессии: `/requirements` без аргументов. Ожидается запрос пути без выбора материала, придуманных значений и записи файла. Подтверждение пустого вызова пока не предоставлено; эта часть со звёздочкой остаётся непроверенной.

Первый прогон с параметром пути получен в приложенном ответе. Формат и тематическая зависимость от LOAN-12 присутствуют. Замечания: ошибка трактовки «старше 7» повторилась; правило review при превышении предела записано как действующее «по регламенту» одновременно с открытым конфликтом reject/review, то есть источник фактически выбран до согласования. Значение LTV 60% указано как approve по материалу; это нельзя считать подтверждением текущего поведения кода. Эти замечания не исправлены в ответе эксперимента.

## Результаты двух параметров

Пользователь предоставил тексты LOAN-12 и CASE-01, а также дополнительный ответ обработки CASE-01. Существование обоих локальных файлов и четыре главных раздела сверены помощником. В последнем CASE-01 внутри «Требований» появились подпункты участников, потока, риск-правил, эскалации и примеров; основные четыре раздела сохранены. Новых REQ/AC не добавлено.

- LOAN-12: возрастные диапазоны 3/7/12/20 лет и пределы 70/60/50/40%, взаимодействие с LTV, конфликт review/reject; результат в `docs/spec/spec_LOAN-12.md`.
- CASE-01: лимиты сумм по типу ТС (2000000/3000000/500000), активные займы, возраст залога, минимальная сумма, перечень сработавших правил и эскалация; результат в `docs/spec/spec_CASE-01.md`. LOAN-12 не подставлен вместо нового материала.

В дополнительном ответе CASE-01 агент явно сообщил: «ID: CASE-01 (явно указан в заголовке материала). Существующий docs/spec/spec_CASE-01.md будет перезаписан результатом текущей обработки источника docs/sources/CASE-01.md». Это не является результатом пустого параметра: исходная строка этого дополнительного вызова не предоставлена, поэтому оснований приписывать ему `/requirements` без аргументов нет.

Первые результаты CASE-01 выбрали «не более двух» и полный перечень причин по регламенту, одновременно оставляя их конфликт с тикетом открытым. Следующий ответ CASE-01 отметил необходимость решения риск-менеджера, но всё ещё содержит эти значения в основных требованиях. Правильная работа параметра не означает согласованность бизнеса; ответы сохранены как результаты проверки команды, не как утверждённая спецификация.

Итог 2.4.2: два разных пути дали разные задачи, ID и файлы результата, формат пользовательской рутины сохранён. Минимальная проверка влияния параметра выполнена; пустой параметр и качество решения конфликтов оцениваются отдельно.

## Чужой вход (2.4.3)

Новый материал, ранее не использованный командой: `docs/sources/CASE-02.md`. Вызов:

```text
/requirements docs/sources/CASE-02.md
```

| Чужой вход | Что сломалось | Что поправлено | Повтор |
|---|---|---|---|
| CASE-02 — решения по скоринговому баллу | Путь, ID и файл определены верно, но поведение на 450/700 выбрано по регламенту как обязательное в T-2, хотя Q-1 оставляет выбор между автоматическим решением и ручной проверкой открытым; вариант тикета исключён в N-2. | В команду добавлена финальная сверка требований с открытыми вопросами: не утверждать спорную ветку и не исключать её как не-цель до согласования. | Повтор получен, но сбой сохранился в T-2, примерах T-6 и N-2; нужно проверить, был ли загружен обновлённый текст команды. |

Первый результат сохранён в локальном `docs/spec/spec_CASE-02.md`: четыре главных раздела, решения по баллу, обоснование, диапазон 0..1000, вопросы об ответе модели и факторах. Старые задачи LOAN-12 и CASE-01 не подставлены. Конфликт источников подтверждён материалом: `[TICKET-CASE-02]` требует на 700 одобрение, на 450 отказ; `[REG-SCORE-11]` п.4.4 запрещает автоматическое решение на границе.

Ошибка видна в самом результате: T-2 говорит «ровно равен порогу (450 или 700) — на ручную проверку», а Q-1 требует подтверждения окончательного поведения. Поэтому переносимость пути прошла, но контроль согласованности требований не прошёл. Исходный ответ не исправлен помощником; повтор должен выполнить агент через ту же команду, а не через промпт с подсказкой о нужном выборе.

Команда не дублирует скилл: добавленный шаг проверяет выполнение существующего правила о конфликтах, сам формат продолжает задаваться SKILL.md. Проверка на машине коллеги не проводилась.

Повторный ответ предоставлен пользователем: T-2 снова назначает ручную проверку на 450 и 700, T-6 повторяет этот исход в S-02/S-04, N-2 исключает автоматизацию границ из требований. Q-1 при этом требует согласования конечного поведения. Помощник не исправлял результат вручную и не считает повтор успешным. Пока неизвестно, не соблюдён новый шаг команды или сессия получила старую инструкцию. Следующая диагностика — спросить в той же сессии о фактически полученном тексте slash-команды без новых действий. Итог задания ожидает успешного повторного прогона, PR блока ещё не открыт.
