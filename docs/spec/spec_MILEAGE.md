# Spec: правило «пробег авто не больше 400 000 км, иначе решение review»

ID задачи: `MILEAGE`. Основа: `docs/intent/intent_MILEAGE.md`. Здесь фиксируется «что
считается сделанным»; как реализовывать — `docs/plan/plan_MILEAGE.md`, реализации
в этой спеке нет. OQ-MILEAGE-01 закрыт ответом постановщика (2026-10-12): `reject`
по LTV сохраняет приоритет — при пробеге больше 400 000 км правило переводит в
`review` только `approve`, решения `review` и `reject` остаются без изменений.

## Входит / не входит

**Входит** (всё — из intent):

- Расчёт решения по заявке на стороне backend учитывает пробег: при пробеге не
  больше 400 000 км решение считается по LTV по действующим правилам; при пробеге
  больше 400 000 км правило переводит в `review` только решение `approve`,
  решения `review` и `reject` по LTV остаются без изменений. — intent «Замысел»,
  ответ в интервью; перевод только `approve` и приоритет `reject` — ответ
  постановщика (2026-10-12).
- Граничные значения порога: 399 999 / 400 000 / 400 001 км. — intent «Constraints» п.1, ответ в интервью.
- Поведение при пустой строке, отсутствующем поле и `null` в поле пробега. — intent «Constraints» п.5, 6, ответ в интервью.
- Сохранение действующей валидации пробега (диапазон 0–500 000 км) без изменений. — intent «Constraints» п.4, ответ в интервью.

**Не входит** (всё — из intent «Не входит» и «Open questions»):

- Фронтенд. — ответ в интервью.
- БД и миграции. — ответ в интервью.
- Seed-данные. — ответ в интервью.
- Расчёт одобряемого лимита по возрасту автомобиля — задача LOAN-12. — ответ в интервью; код: backend/config/rules.php (`ltv_by_age`, строки 53–58).
- Изменение структуры ответа API и добавление причины `review`. — intent «Constraints» п.7, ответ в интервью.
- Изменение валидации пробега (диапазон, тексты ошибок) — остаётся как есть. — intent «Constraints» п.4, ответ в интервью.
- Изменение обработки пустой строки пробега (превращение её в ошибку валидации) — отдельная задача, см. OQ-MILEAGE-02. — intent «Open questions» п.2.

## Требования

Одно атомарное проверяемое утверждение на REQ, источник у каждого.

- **REQ-MILEAGE-01.** Заявка с пробегом не больше 400 000 км решается по LTV по
  действующим правилам; задача MILEAGE не меняет её решение.
  Источник: intent «Замысел», первое предложение (ответ в интервью); граница
  «не больше — включительно» — intent «Constraints» п.1 (ответ в интервью).
- **REQ-MILEAGE-02.** Заявка с пробегом больше 400 000 км в пределах действующей
  валидации (400 001–500 000 км), решение которой по LTV — `approve`, получает
  `review` вместо `approve`.
  Источник: intent «Constraints» п.2 (ответ в интервью); intent «Замысел», второе
  предложение; диапазон действия правила — производное от порога 400 000
  (intent «Constraints» п.1) и границы валидации 500 000 (intent «Constraints» п.4).
- **REQ-MILEAGE-03.** Заявка с пробегом больше 400 000 км, решение которой по
  LTV — `review` или `reject`, сохраняет это решение без изменений: `review`
  остаётся `review`, `reject` остаётся `reject`; `reject` при LTV > 85 сохраняет
  приоритет над `review` по пробегу.
  Источник: ответ постановщика (2026-10-12), закрывший OQ-MILEAGE-01; intent
  «Constraints» п.3 (ответ в интервью — исходная формулировка вопроса).
- **REQ-MILEAGE-04.** Валидация пробега не меняется: проходят заявки с пробегом
  0–500 000 км; при пробеге больше 500 000 км — ошибка валидации по полю
  `mileage`, до расчёта решения заявка не доходит.
  Источник: intent «Constraints» п.4 (ответ в интервью); код: backend/config/rules.php (`vehicle.max_mileage_km` = 500000, строка 23); код: backend/src/Domain/ApplicationValidator.php:43–46.
- **REQ-MILEAGE-05.** Отсутствующее поле `mileage` и значение `"mileage": null` —
  ошибка валидации по полю `mileage`, до расчёта решения заявка не доходит.
  Источник: intent «Constraints» п.5 (ответ в интервью); код: backend/src/Domain/ApplicationValidator.php:43 (`(int) ($payload['mileage'] ?? -1)`), :44 (проверка `< 0`).
- **REQ-MILEAGE-06.** Пустая строка в поле `mileage` приводится к 0 и допускается
  валидацией; в задаче MILEAGE текущее поведение сохраняется.
  Источник: intent «Constraints» п.6 (ответ в интервью); сохранение поведения в
  рамках MILEAGE согласовано постановщиком на этапе спеки (2026-10-12);
  изменение поведения — вне scope, см. OQ-MILEAGE-02.
- **REQ-MILEAGE-07.** Решение остаётся одним из `approve` / `review` / `reject`;
  структура ответа API не меняется; поле «причина review» не добавляется.
  Источник: intent «Constraints» п.7 (ответ в интервью); intent «Не входит», последний пункт.

## Критерии приёмки

Формат Given / When / Then, ссылка на REQ у каждого. Общие условия: остальные
поля заявки валидны; LTV задаётся валидными запрошенной суммой и оценочной
стоимостью (код: backend/config/rules.php, `amount`: 50 000–2 000 000 ₽, строки
26–29); ошибка валидации — ответ HTTP 422 с ошибкой по полю `mileage`, решение не
рассчитывается (код: backend/src/Http/ApplicationController.php:29–31).

Границы порога 400 000 км:

- **AC-MILEAGE-01** (REQ-MILEAGE-01). Given заявка с пробегом 399 999 км и LTV 50 %
  (по LTV — `approve`). When рассчитано решение. Then `approve` — правило пробега
  не срабатывает, решение по LTV.
  Числа: 399 999 — порог 400 000 минус 1 (intent «Constraints» п.1); LTV 50 % < 60 % — код: rules.php (`ltv.approve_max`, строка 44).
- **AC-MILEAGE-02** (REQ-MILEAGE-01). Given заявка с пробегом ровно 400 000 км и
  LTV 50 %. When рассчитано решение. Then `approve` — порог «не больше» включительный.
  Числа: 400 000 — intent «Constraints» п.1 (ответ в интервью); LTV 50 % — код: rules.php (`ltv.approve_max`).
- **AC-MILEAGE-03** (REQ-MILEAGE-02). Given заявка с пробегом 400 001 км и LTV 50 %
  (по LTV — `approve`). When рассчитано решение. Then `review`.
  Числа: 400 001 — первая отметка срабатывания правила (intent «Constraints» п.1, ответ в интервью).

Сочетания с LTV при пробеге выше порога:

- **AC-MILEAGE-04** (REQ-MILEAGE-03). Given заявка с пробегом 400 001 км и LTV 70 %
  (по LTV — `review`). When рассчитано решение. Then `review` — решение по LTV
  сохраняется без изменений.
  Числа: 60 % ≤ 70 % ≤ 85 % — код: rules.php (`ltv.approve_max`, `ltv.review_max`,
  строки 44–45); сохранение `review` — ответ постановщика (2026-10-12).
- **AC-MILEAGE-05** (REQ-MILEAGE-02). Given заявка с пробегом 500 000 км и LTV 50 %.
  When рассчитано решение. Then `review` — верхняя граница диапазона действия
  правила.
  Числа: 500 000 — код: rules.php (`vehicle.max_mileage_km`, строка 23).
- **AC-MILEAGE-06** (REQ-MILEAGE-03). Given заявка с пробегом 400 001 км и LTV 90 %
  (по LTV — `reject`). When рассчитано решение. Then `reject` — `reject` сохраняет
  приоритет над `review` по пробегу.
  Числа: 90 % > 85 % — intent «Constraints» п.3 («LTV > 85», ответ в интервью);
  приоритет `reject` — ответ постановщика (2026-10-12); код: rules.php
  (`ltv.review_max`, строка 45).

Валидация пробега без изменений:

- **AC-MILEAGE-07** (REQ-MILEAGE-04). Given заявка с пробегом 0 км и LTV 50 %.
  When рассчитано решение. Then заявка валидна, `approve` — нижняя граница
  диапазона допустима, правило пробега не срабатывает.
  Числа: 0 — intent «Constraints» п.4 (ответ в интервью); код: ApplicationValidator.php:44.
- **AC-MILEAGE-08** (REQ-MILEAGE-04). Given заявка с пробегом -1 км. When проходит
  валидация. Then ошибка валидации по полю `mileage`, решение не рассчитывается.
  Числа: -1 < 0 — за нижней границей (код: ApplicationValidator.php:43–44).
- **AC-MILEAGE-09** (REQ-MILEAGE-04). Given заявка с пробегом 500 001 км. When
  проходит валидация. Then ошибка валидации по полю `mileage`, решение не
  рассчитывается.
  Числа: 500 001 — 500 000 плюс 1 (код: rules.php `vehicle.max_mileage_km`, строка 23).

Пустой и неизвестный пробег:

- **AC-MILEAGE-10** (REQ-MILEAGE-05). Given поле `mileage` в заявке отсутствует.
  When проходит валидация. Then ошибка валидации по полю `mileage`, решение не
  рассчитывается.
- **AC-MILEAGE-11** (REQ-MILEAGE-05). Given `"mileage": null`. When проходит
  валидация. Then ошибка валидации по полю `mileage`, решение не рассчитывается.
- **AC-MILEAGE-12** (REQ-MILEAGE-06). Given `"mileage": ""` и LTV 50 %. When
  проходит валидация и расчёт решения. Then пробег принят равным 0, заявка
  валидна, решение `approve` — согласованное сохранение текущего поведения;
  изменение — вне scope (OQ-MILEAGE-02).
  Числа: приведение `""` к 0 — код: ApplicationValidator.php:43 (приведение к int).

Структура ответа:

- **AC-MILEAGE-13** (REQ-MILEAGE-07). Given любой из запросов AC-MILEAGE-01 –
  AC-MILEAGE-12, прошедший валидацию. When сформирован ответ API. Then поле
  `decision` принимает значение `approve`, `review` или `reject`; набор полей
  ответа совпадает с текущим, новых полей нет, в том числе поля причины `review`.
  Состав полей ответа — код: backend/src/Http/ApplicationController.php:44–50, 64–69.

## Открытые вопросы из intent

- **OQ-MILEAGE-01** — из intent «Open questions» п.1: должен ли пробег > 400 000 км
  давать `review` даже при LTV > 85 (`reject`), или `reject` сохраняет приоритет?
  Статус: **закрыт — ответ постановщика (2026-10-12)**: `reject` сохраняет
  приоритет; при пробеге > 400 000 км в `review` переводится только `approve`,
  `review` и `reject` не меняются. Зависимые места: REQ-MILEAGE-03,
  AC-MILEAGE-04, AC-MILEAGE-06 — однозначны и больше не требуют согласования.
- **OQ-MILEAGE-02** — из intent «Open questions» п.2: обработка пустой строки
  пробега как ошибка валидации. Статус: **перенесён в отдельную задачу** (вне
  scope MILEAGE). В рамках MILEAGE зафиксировано сохранение текущего поведения:
  пустая строка приводится к 0 и допускается (REQ-MILEAGE-06, AC-MILEAGE-12);
  сохранение уже согласовано постановщиком, изменение — вне scope.
