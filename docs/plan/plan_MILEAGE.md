# План: правило «пробег авто не больше 400 000 км, иначе решение review»

ID задачи: `MILEAGE`. Основа: `docs/setup/code_map.md` (сверен с кодом), ответ scout из `docs/setup/agents.md`.

Суть: заявка с пробегом до 400 000 км включительно решается по LTV как раньше;
пробег больше 400 000 км даёт решение `review` (в пределах действующей валидации —
т.е. реально срабатывает для 400 001–500 000 км, см. Риски и Вопросы).

## Тесты

Граничные значения (отдельными строками):

- Пробег 399 999 км → решение не меняется (по LTV; approve остаётся approve).
- Пробег 400 000 км → порог НЕ срабатывает, решение по LTV (правило «не больше 400 000» включительно).
- Пробег 400 001 км → `review` даже при низком LTV (approve понижается до review).
- Отсутствующее поле или `null` → `(int) ($payload['mileage'] ?? -1)` даёт -1; `ApplicationValidator` выбрасывает `ValidationException`, до `DecisionEngine` заявка не доходит.
- Пустая строка `mileage: ""` → текущий код приводит её к 0 и допускает. Нужен отдельный тест и согласование, должна ли пустая строка считаться ошибкой; не смешивать её с отсутствующим полем.

Прочие случаи:

- LTV > 85 (reject) + пробег > 400 000 → ожидаемое решение определить после согласования приоритета, не закреплять предположение тестом заранее.
- LTV 60–85 (review) + пробег > 400 000 → `review`.
- Пробег > 500 000 → валидационная ошибка, решение не считаем (проверка остаётся в `ApplicationValidator`).

## Риски

- Существующая проверка `max_mileage_km` (валидация 0–500 000) не трогается, но пересекается с новым правилом: правило реально срабатывает только на диапазоне 400 001–500 000. Если заказчик ожидает `review` и для пробега > 500 000 — не сработает, будет ошибка валидации.
- Приоритет reject vs review при большом пробеге не согласован. Вариант «reject старше» — только предложение; если нужен безусловный review, порядок проверок будет другим. До реализации требуется решение заказчика.
- Смена сигнатуры `DecisionEngine::decide()` ломает все текущие вызовы и тесты — правка в `AssessmentService` и `DecisionEngineTest` обязательна, композерских/внешних вызовов нет (проект монолитный).
- Форма и БД не меняются: `mileage_km INT UNSIGNED NOT NULL` (`db/schema.sql:22`) вмещает все значения валидации; миграции не нужны.
- Не входит: расчёт `approved_limit` по `ltv_by_age` (задача LOAN-12), изменение текста ошибок валидации, фронтенд, seed-данные, справочник цен за пробег.
- `make test` должен остаться зелёным до и после; `make verify` в проекте нет.
